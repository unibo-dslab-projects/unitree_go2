go2_mapping_bringup

go2_mapping_bringup starts the mapping chain. It has no code: only launch files that start the nodes, and config files that hold their settings.

What. A ROS 2 package with three launch files and three config files. One command starts go2_preprocessor, Point-LIO and map_builder, gives each its settings, and connects them with the right topic names.

Why. The chain has three programs from three places, and they only work together if the details match:

  • each one needs its own settings file, and a wrong node name makes ROS ignore the file without an error;
  • Point-LIO reads the preprocessor’s topics, and map_builder reads Point-LIO’s topics;
  • the calibration file must reach the preprocessor, or the map comes out tilted;
  • the robot and the laptop must use the same DDS (the layer ROS uses to send messages), or they do not see each other.

This package fixes all of these in one place, so nobody types them by hand.

When. Every time you map. tools/mapping/map.sh calls it for you.

Where it sits

The package does not run anything itself. It tells ROS what to start. The three nodes it starts have their own pages: go2_preprocessor and map_builder.

What is inside

Quick start

The normal way, on the robot computer. The script checks the topics, the disk and the calibration, and then calls the launch file:

tools/mapping/map.sh

The launch file alone:

ros2 launch go2_mapping_bringup mapping.launch.py \
    calibration_file:=$HOME/calibration/current.yaml

calibration_file has no default. This is on purpose: without it the preprocessor would use CMU’s mount values, and the map would come out tilted. Launch stops at once if you forget it.

The same command works live and with ros2 bag play. All nodes use the stamps inside the messages and not the clock, so there is no use_sim_time switch (Foxy’s bag player has no --clock).

How it works

Who starts whom

mapping.launch.py is a list of actions. ROS runs them in order. The last one includes another launch file, but only when a condition is true.

Both mapping.launch.py and laptop.launch.py include map_builder.launch.py. One of them has the condition true, the other false, so map_builder starts exactly once. Step 3 is explained in Which DDS.

What happens at start-up

The three nodes start together, not one after the other. Nothing waits for the previous node to be ready. This is fine because a node that has no input yet just waits.

Point-LIO needs about 3 s to start, then it takes gravity and its first map from the next seconds. The robot must stand still for that time. map.sh prints KEEP THE ROBOT STILL for 10 s.

Where the data flows

The launch files do not carry data. They only set the names so that the nodes find each other.

Where the names are set:

ConnectionSet inHow
Go2 to preprocessorgo2_preprocessor codeFixed in the code
Preprocessor to Point-LIOpoint_lio.yamllid_topic and imu_topic
Point-LIO to map_buildermap_builder.launch.pyremappings: cloud becomes /cloud_registered, odom becomes /aft_mapped_to_init

map_builder only knows the short names cloud and odom. The launch file points them at Point-LIO. The frame of /cloud_registered is camera_init, Point-LIO’s world frame.

How the settings reach each node

Each file starts with a key: the node name. ROS gives the file to the node with that name and ignores it for all others. If the key and the name differ, ROS says nothing and the node runs with its defaults. This is why the launch file comments say “the node name must stay go2_preprocessor”.

For the preprocessor two files are given. The second wins when both set a value. The robot box is in preprocessor.yaml and the measured numbers are in the calibration file, so they never clash.

output_dir is not in map_builder.yaml. The launch file sets it, because ~ must mean the home folder of the machine that runs the node, and that is only known at launch time.

Robot or laptop

By default everything runs on the robot. You can move map_builder to the laptop. Point-LIO then sends its scans over Wi-Fi.

# on the robot
ros2 launch go2_mapping_bringup mapping.launch.py calibration_file:=... map_builder_host:=laptop
# on the laptop
ros2 launch go2_mapping_bringup laptop.launch.py map_builder_host:=laptop

The value must be the same on both machines. Two commands that say robot and laptop would start two map_builders (the second stops itself) or none. On the laptop with robot, the launch starts nothing.

Which DDS

DDS is the layer under ROS that sends the messages. Foxy uses Fast-RTPS by default. The robot uses CycloneDDS. Two machines with different DDS do not talk to each other. Point-LIO also hangs on Ctrl-C with Fast-RTPS.

Both launch files therefore set RMW_IMPLEMENTATION to rmw_cyclonedds_cpp, but only if the shell has no value yet. A value you set yourself is kept.

What happens on Ctrl-C

Ctrl-C reaches every node. map_builder writes the map into a new folder <output_dir>/<time of the first scan, UTC>/. The Point-LIO message is a known flaw of its exit. It comes after the map is saved and does not cost data.

point_lio.yaml

Taken from CMU’s utlidar.yaml. The file has about 60 values, each with a comment. These are the ones that differ from CMU or that you may want to change:

ParameterValueWhy
lid_topic, imu_topicthe preprocessor’s two topicsPoint-LIO reads the corrected data, not the robot’s
extrinsic_T, extrinsic_Rzero, identityThe preprocessor already turned lidar and IMU into one body frame
init_map_size5000About 0.5 s of scans. CMU’s 10 builds the first map from one scan, mostly floor, and the gyro bias runs away
gravity, gravity_align(0, 0, -9.81), trueThe IMU is scaled to 9.81 at rest. Without gravity, Point-LIO reads it as the robot speeding up
acc_norm9.81The accelerometer unit is m/s^2
satu_acc40The body accelerometer peaks at 29 m/s^2 at foot strikes. CMU’s 30 would flag them
blind0.5 mDrops lidar points closer than this. It removes the robot’s own body
filter_size_surf, filter_size_map0.1 mVoxel size of the scan and of Point-LIO’s map. Smaller means finer, more memory and CPU
use_imu_as_inputfalseThe IMU is a measurement of the filter, which holds up in rough motion
pcd_save_enfalsePoint-LIO would overwrite one file per run. map_builder saves each run in its own folder

map_builder.yaml

ParameterValueMeaning
voxel_size0.05 mOne point per voxel. On 2026-10-19_line_01: 45,195 points at 0.05, 14,476 at 0.10
delta_rate_hz2How often new voxels are sent
pose_rate_hz10How often the robot pose is sent
full_map_rate_hz0The whole map on a topic. 0 is off, because every message holds the whole map

Calling the save service and then stopping gives two folders, <time> and <time>_1.

preprocessor.yaml

Only the robot_box. See go2_preprocessor for what the box does.

Build and test

The package only copies files. Build it with everything it starts:

cd ~/unitree_go2
source ~/unitree_ros2/setup.sh
vcs import src < go2.repos
colcon build --packages-up-to go2_mapping_bringup

vcs import fetches Point-LIO, pinned to one commit in go2.repos. There are no tests. A launch file has no logic worth a unit test, and the full run is tried by map.sh on a bag.

Known gaps

  • No test for the launch files. A typo in a node name or a topic is found only by running the chain. The last full run was on the laptop with a bag (2026-10-19_line_01), not on the robot.
  • map_builder_host must match by hand. Nothing checks that the two machines have the same value. map_builder stops a second copy of itself, but a wrong pair that starts none is not noticed.
  • The robot box is still CMU’s. See go2_preprocessor.
  • The RMW_IMPLEMENTATION default hides a mismatch. A shell with rmw_fastrtps_cpp already set is kept, and the two machines then do not see each other, with no error.
  • laptop.launch.py starts nothing with robot. It is there for the viewer bridge, which is not written yet.
