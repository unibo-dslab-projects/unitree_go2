Unitree Go2

go2_preprocessor

go2_preprocessor turns the raw Go2 lidar cloud and body IMU into what Point-LIO expects: both in the body frame, corrected with the numbers from go2_calibration.

What. One ROS 2 node (ros2 run go2_preprocessor go2_preprocessor). It runs while you map. It listens to the raw lidar cloud and to the robot state, fixes both with the calibration file, and publishes two clean topics for Point-LIO:

  • the cloud, moved into the body frame, with the ranges shortened and the robot’s own points removed;
  • the body IMU, with the gyroscope bias removed and the accelerometer scaled to 9.81.

Why. Point-LIO builds the map from a cloud and an IMU. They must share one frame and tell the truth. The raw Go2 data does neither:

  • the cloud is in the lidar frame, and the lidar is mounted upside down and tilted;
  • every lidar range reads about 0.11 m too long;
  • the body IMU has a bias, and a still accelerometer reads 9.44 m/s^2 instead of 9.81;
  • the lidar sees the robot’s own back.

Fed raw, Point-LIO draws a tilted and stretched map.

When. Every time you map. It is the first node of the mapping chain, and mapping.launch.py starts it.

Where it sits

The measured numbers (lidar_to_body, body_imu, range_offset) come from the go2_calibration file. The robot box is written by hand in preprocessor.yaml. The lidar’s own IMU (/utlidar/imu) is not used: its accelerometer is synthetic.

Intensity, ring and time of each point, and the stamp of the cloud, pass through unchanged.

Quick start

With the whole mapping chain (preprocessor, Point-LIO, map builder):

ros2 launch go2_mapping_bringup mapping.launch.py calibration_file:=$HOME/calibration/current.yaml

tools/mapping/map.sh starts the same chain with the current calibration. The node alone:

ros2 run go2_preprocessor go2_preprocessor --ros-args \
    --params-file src/go2_mapping_bringup/config/preprocessor.yaml \
    --params-file $HOME/calibration/current.yaml

The node name must stay go2_preprocessor: both files are keyed by it, and a different name makes ROS ignore them without an error.

How it works

The code in one picture

Everything is one executable. The files in the box are plain C++ with Eigen (a matrix library), except the node, which needs ROS. An arrow means “uses”.

Start-up

The node reads every setting once, when it starts. All of them are read-only parameters: a later ros2 param set fails with an error instead of being silently ignored.

rotation_from_parameter refuses a matrix that is not a rotation (stretched axes, or a mirror image), so a typo in the file stops the node at start-up. The log line calibration: shows whether the file was applied: look for your numbers there.

A cloud message

The order matters. The robot box is written in the body frame, so the points are turned before the box is applied. The ranges are shortened first because the offset belongs to the lidar: it is measured along each ray from the lidar’s centre. A cloud that cannot be read (data shorter than its declared size, or a missing field) is logged and skipped.

Example. Real run of the actual code, with the calibration of 2026-10-19 (lidar_to_body and range_offset 0.1129 m). The points are made up: they were computed back from a known place in the body frame, with every range 0.1129 m too long, the way the lidar reads them.

An IMU message

1 to 1.5 % of the messages repeat the previous sample, with the same stamp and the same values. Point-LIO would take the copy as one more measurement at the same instant, so the node drops it.

The stamp is the one inside the message, which uses the lidar’s clock, and not the receive time. The orientation and the covariances stay at their defaults (“unknown”): Point-LIO reads only the rates and the acceleration.

Example. The body IMU at rest on our Go2: the accelerometer reads (-0.146, -0.133, 9.444), with length 9.446. The scale 9.81 / 9.446 = 1.0385 turns it into (-0.152, -0.138, 9.808). The small sideways parts grow by the same factor, because it is a scale and not a bias.

Build and test

Needs Unitree’s unitree_go messages. On the robot they come with ~/unitree_ros2:

cd ~/unitree_go2
source ~/unitree_ros2/setup.sh
colcon build --packages-select go2_preprocessor
colcon test --packages-select go2_preprocessor && colcon test-result --verbose

Four test programs, one per file: test_convertor (round trip and layout), test_schemas (the box limits), test_robot_utils (turn, filter, and both in order), test_imu_transform. Each one compiles the file it tests again, because the code lives in the executable and not in a library.

Known gaps

  • The box is still CMU’s. robot_box was made for CMU’s lidar_to_body translation (0, 0, -0.046825). Ours is (0.282, 0, 0). The comment in preprocessor.yaml says to check it in RViz with the real calibration. Not done yet.
  • No calibration file means CMU’s mount. Started alone without a calibration file, the node uses CMU’s rotation and no IMU correction, and the map comes out tilted. mapping.launch.py requires calibration_file, but ros2 run does not. Only the start-up log shows it.
  • calibration.cpp has no unit test. It is what stops a stretched or mirrored rotation, and the wrong number of values. The four test programs do not include it. shorten_ranges has none yet either.
  • The log line counts range drops as robot points. robot points removed is points in minus points out, so it also counts the points dropped for being closer than range_offset.
