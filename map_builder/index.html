map_builder

map_builder collects Point-LIO’s output into one map and one path, and saves both to disk.

What. One ROS 2 node (ros2 run map_builder map_builder). It listens to the scans and the poses that Point-LIO publishes. It keeps the scans in a voxel map: space is cut into small cubes, and each cube holds one point. It also keeps every pose, in a list. It publishes the new cubes while you map, and on Ctrl-C it writes map.pcd and trajectory.tum.

Why. Point-LIO sends the same wall again with every scan, about 10 times a second. Saved as they come, the points would pile up and the file would be huge. Point-LIO also does not save anything by default. map_builder removes the repeats and keeps the result, so a walk ends with two small files that the rest of the thesis can use.

When. Every time you map. mapping.launch.py starts it, on the robot or on the laptop.

Where it sits

The inputs are called cloud and odom inside the node. go2_mapping_bringup points them at Point-LIO’s two topics. The frame of the scans is camera_init, Point-LIO’s world frame: the origin is where the robot stood at the start, and x points where it looked.

What it does

DataWhat the node does
Each scanPuts every point in a cube. A cube that is already full ignores the new point
Each poseAppends it to the path. A pose that is not newer than the last one is skipped
New cubesSends them as a delta twice a second
The whole mapOn request: a service answers with every point. Or on a topic, if you turn it on
On saveWrites the map as a PCD file and the path as a TUM file

Quick start

With the whole chain, which is the normal way:

tools/mapping/map.sh

The node alone, if Point-LIO runs elsewhere:

ros2 run map_builder map_builder --ros-args \
    --params-file src/go2_mapping_bringup/config/map_builder.yaml \
    -p output_dir:=$HOME/maps \
    -r cloud:=/cloud_registered -r odom:=/aft_mapped_to_init

Save in the middle of a run, without stopping:

ros2 service call /map_builder/save std_srvs/srv/Trigger

The answer holds the folder name. A run is written to <output_dir>/<time of the first scan, UTC>/, for example ~/maps/2026-10-19T14:35:23/.

How it works

The code in one picture

The code is split in three parts, so that the maths does not need ROS and a test does not need PCL. An arrow means “uses”.

voxel_count is a small program with no ROS. It loads a PCD file and puts it in a voxel map twice. The second time nothing must be added: it proves that no two saved points share a cube.

Start-up

All the parameters are read-only: a later ros2 param set fails with an error.

The run_id tells a viewer that a new map has begun. The check after 2 s is there because two map_builders on the same topics would send two different maps, and a viewer cannot tell them apart.

A cloud message

A cloud that cannot be read (its data is shorter than width * height * point_step, or a field is missing) is logged and skipped. The first scan fixes the map frame and the name of the save folder. Every log line “Voxels N, added M points from cloud” comes at most every 2 s.

The voxel map

VoxelMap::insert does this for every point. A point that is not a number (NaN or infinity) is skipped.

floor, not a plain cast, because a cast rounds towards 0 and puts -0.03 and +0.03 in the same cube. The map is a hash map (unordered_map) with the key hashed from three large primes, a method called spatial hashing.

Example. The numbers are made up. The voxel size is 0.05 m.

Point (x, y, z)x, y, z divided by 0.05KeyResult
(1.23, -0.03, 0.51)24.6, -0.6, 10.2(24, -1, 10)new, stored
(1.24, -0.04, 0.52)24.8, -0.8, 10.4(24, -1, 10)same cube, ignored
(1.26, -0.03, 0.51)25.2, -0.6, 10.2(25, -1, 10)new, stored

The first point of a cube wins. It is not averaged with the later ones.

Real numbers. On the straight walk 2026-10-19_line_01 (5.4 m), voxel 0.05 m gives about 44,700 points. Voxel 0.10 m gave 14,476 points on the same walk, and 0.05 m gave 45,195 on an earlier run.

An odometry message and the three timers

Nothing is sent from the callbacks. They only store. Three timers send what was stored.

The delta holds only the new cubes, one point each, so it stays small. seq counts 1, 2, 3 and so on inside one run. stamp is the newest scan inside the delta. A delta with no new points is not sent, so a still robot sends nothing.

How a viewer keeps in step

A viewer can join late or miss a message. The rules are in the message files MapDelta.msg and GetMap.srv.

get_map first sends the pending points as a delta. This way the snapshot matches seq exactly, and the viewer never has a hole between the snapshot and the next delta.

Save

Saving twice in one run gives two folders, <time> and <time>_1. Save fails with map is empty if no scan came, and with output_dir is not set if the node has no output folder. A failed save at exit is logged and does not crash the node.

The message types are in the small package go2_mapping_msgs: MapDelta.msg (header, run_id, seq, a PointCloud2 of the new points) and GetMap.srv (no request, answers with run_id, seq and a PointCloud2 of all points).

Output files

map.pcd has one point per cube, binary, fields x y z intensity, in metres, frame camera_init.

trajectory.tum has one line per pose: stamp x y z qx qy qz qw. The stamp is in seconds with 9 digits after the dot. Example line, made up:

1760884523.123456789 1.204300 -0.031200 0.002100 0.000100 -0.002300 0.014000 0.999900

The path starts at (0, 0, 0). For a walk that ends on its start mark, the distance of the last pose from the origin is the drift of Point-LIO.

Build and test

cd ~/unitree_go2
source ~/unitree_ros2/setup.sh
vcs import src < go2.repos
colcon build --packages-up-to map_builder

It needs PCL (the point cloud library) for the PCD file. The package has no unit tests yet. It was checked by replaying a bag through the whole chain on the laptop. The steps are in src/map_builder/README.md. A correct run of 2026-10-19_line_01 at -r 0.25 gives:

If the map has about 18,700 points and the end is at x 7.36 m, Point-LIO ran with the old 0.5 m filter size. Check filter_size_surf and filter_size_map in point_lio.yaml.

Known gaps

  • No unit tests. VoxelMap, Trajectory and map_io are plain C++ and easy to test. The CMake file has the lines ready but commented out. The only checks are the bag replay and voxel_count.
  • The first point of a cube stays, the rest are lost. There is no average. A noisy first point stays in the map for the whole run.
  • Nothing is ever removed. A person who walks through the scene leaves points that stay in the map. Point-LIO has no loop closing either, so drift is not corrected later.
  • A pose can be published and not saved. on_odometry ignores the answer of Trajectory::add. A pose that is not newer than the last is skipped in the file but still goes to /map_builder/pose.
  • A save is lost if the node is killed. The map is only in memory. save_on_exit works on Ctrl-C. A crash or kill -9 loses the run, unless save was called before.
  • A scan with another frame is dropped with a warning only. The warning comes at most every 2 s.
  • Two nodes starting together. The check counts publishers after 2 s. From reading the code, not from a test, two nodes that start together could both see two and both stop.
